## Side by side comparison of features
Currently we have 6 different feature sets for derived_8.2, containing both good and bad ones (in terms of performance), so we can know what features to include and what traps to avoid for the next iteration.

### Unexpected findings
Previously we found out the feature sets are struggle with 2024 test set-- being a valley in the year-by-year performance. But surprisingly `OVERALL_SELECTED_FEATURES_V0` has a huge jump in 2024 while other years are significantly lags behind, perhaps we can look into what features are helping 2024.

Specifically on 2-24, V0 uses direct rolling statistics over the current year's local observation window (e.g., `V_rollmin_G_API_kobs30` and `V_rollmin_LST_modis_kobs30`), allows it to capture the actual sub-seasonal drydown and heating trends of 2024 directly, without being biased by smooth climatological averages.

But in a broader view, the importance of each individual feature varies significantly across different years!
For example, in V0, the feature `SMAP_sm_pm_interp_lag1` was somehow useful in 2024 and 2025, but completely uncorrelated in 2023, that local soil moisture dried out significantly (mean: 0.1668), but coarse SMAP data failed to capture this localized drydown (mean remained 0.3557), so it become complete noise in 2023. This actually corresponding to the feature importance chart in `MDR-v25.ipynb` that temporal weighted vs unweighted model has quite different feature importance ranking.

Thus, MoE architecture still make sense because we can give different feature sets different specialists. But new question emerged: how good is the model filtering out noise? do we really need separate specialists for different feature sets, or can we just use a single model with all features and let it learn to ignore the noise? Still, if the newly divided regimes each requires a different set of features, then it means the regime separation is useful.

## Hyperparameter Tuning
Currently the model is still somewhat regression to the mean and there're amount of rows is doubled, I'm suspecting the model doesn't have enough capacity.

## Generalization
The *Regression to the Mean* generalization failure doesn't mean the model is underfitting, instead it might be overfitting that the test data is never seems before so XGBoost fallbacks to the mean.

Turns out the models are quite overfitting according to `derived_8.2-eval-2.0`. Despite the performance isn't negatively impacted, we severely wastefully trained the model with rounds. Looks like we don't need above 1000 for any learning rate, and the model is already converged. 

Still, XGBoost's performance won't hurt from overfitting, so not necessary to directly make it un-overfitted.

#### Many Soil Moisture in SNOTEL `.stm` Files are consecutively zero
During verification, there're soil_moisture_5cm being  exactly 0.0 for several SNOTEL stations (BurntMountain_WA and HartsPass_WA_515). That derived_9.0 dataset doesn't have any zero soil moisture values.
Upon inspecting the input `.stm` files, I found that many soil moisture values are **consecutively zero**.
Currently, `SNOTELPipe` Reads .stm values as-is via `pd.to_numeric(errors='coerce')`. It ignores the Quality column (which has flags like D02,D03) — so even if NRCS flagged those measurements, we accept them. Multiple sensors at the same depth are averaged, so zeros from one sensor pull the average down. However, the *ISMN quality flags* are these rows are actually **good**.

#### Bug Discovered: MODIS NDVI is 100% Null
During verification, **`NDVI_modis` is 100% null across all dates and stations**.

* **Cause:** In [satellite_pipe.py](file://src/pipeline/pipes/satellite_pipe.py#L18), the GEE collection asset is hardcoded as:
    ```python
    MODIS_NDVI = "MODIS/006/MOD13C2"
    ```
    NASA has retired MODIS Version 6 (006) products, and this collection was deleted from Google Earth Engine's catalog, causing all Earth Engine queries for it to return an error/no data.
* **Why did this not break model training?** 
    In both the `derived_8.0` and `derived_9.0` splits, there is no `NDVI_modis` column. Instead, the models train on **`F_NDVI`**, which is computed dynamically from Sentinel-2 bands (`s2_b4` and `s2_b8`) using the `compute_ndvi` function in [feature_pipe.py](file://src/pipeline/pipes/feature_pipe.py#L51).

##### How to fix the MODIS NDVI bug:
I tested the newer MODIS version 6.1 asset **`MODIS/061/MOD13Q1`** (a standard 250m global 16-day NDVI collection) directly in GEE, and it returns valid values.

#### The Catch about MODIS NDVI
The code did use `MODIS/061/MOD13Q1` originally, but [later](https://github.com/KerryCheon/MDR-Project/commit/4450f4f4ea7a55e1e4f4f364e6d794ac15031e08) switched to `MODIS/006/MOD13C2` for some reason. 
Sentinel-2 actually provides similar high-resolution local NDVI data of `MODIS/061/MOD13Q1`; and the deprecated MODICS can produce broad regional-scale background vegetation baseline rather than duplicating local dynamics.
**Fix of The Fix**: use `MODIS/061/MOD13A3` that can also provide coarse, monthly NDVI data.

#### False Alarm: `[WARNING] pipeline.snotel.*: No precipitation columns found. Skipping rolling rain features.`
This warning occurs during the raw data parsing stage of the pipeline for Sourdough Gulch (and all other SNOTEL stations). It is **harmless** and does not result in missing features in your final dataset. 

Here is a detailed breakdown of why this happens, why it is safe to ignore, and how we can clean it up.


##### Why the Warning is Logged

1. **Local Raw Files:** SNOTEL stations in the project only have soil moisture data in their raw directories (e.g., `src/pipeline/data/raw/SourdoughGulch/` contains only `sm_*.stm` files).
2. **Early Parser Step:** During the second step of the pipeline execution in `main.py`, the `ParsePipe` delegates to `SNOTELPipe`.
3. **No Precipitation Columns Found:** Since `add_rolling_rain: true` is configured in `config.yaml` for SNOTEL stations, `SNOTELPipe.run()` calls `add_rolling_rain_features()`. Because the raw files contain only soil moisture, no precipitation columns (`precip`, `rain`, `ppt`, or `Rain_sat`) exist at this parsing stage. The warning is logged at line 164:
   ```python
   self.logger.warning("No precipitation columns found. Skipping rolling rain features.")
   ```

##### Why it is Harmless

* **Weather Enrichment:** Later in the pipeline, `WeatherPipe` runs and fetches daily historical precipitation data (`rain_mm` and `precip_mm`) via the Open-Meteo API.
* **Rolling Features:** After the weather data is merged, `FeaturePipe` runs and computes the 3-day rolling rain feature (`rain_3d`) from `rain_mm`:
   ```python
   if "rain_mm" in df.columns:
       df["rain_3d"] = (
           pd.to_numeric(df["rain_mm"], errors="coerce")
           .fillna(0)
           .rolling(window=3, min_periods=1)
           .sum()
       )
   ```
* **Verification:** The final output file `src/pipeline/data/processed/sourdough/final.csv` correctly contains the `rain_mm`, `precip_mm`, and `rain_3d` columns.

##### How to Clean This Up

If you want to prevent these false warning messages from cluttering your pipeline log, we can do one of the following:

1. **Option A (Code change):** Downgrade the log message in snotel_pipe.py from `.warning()` to `.info()` or `.debug()`.
2. **Option B (Config change):** Set `add_rolling_rain: false` for all SNOTEL stations in config.yaml, since rolling rain features are already successfully generated by FeaturePip.

# Plan: `derived_8.4-eval-1.3` — 54-Backbone Two-Regime Clustering + Parallel GPU Workers

## Objective

Create `notebooks/experiment/derived_8.4-eval-1.3/` as a copy of `derived_8.4-eval-1.2` (all
existing code and artifact logic), with two changes per the user request:

1. **New clustering configuration `Clustering_Backbone54_k2`**: KMeans(k=2) fitted on the
   **same 54 shared-backbone features as the single-regime global model** (`Global_Single_54`),
   so the paper presents the two-regime model as *developed from the single-regime model*
   (same 54 features for routing + base features), without a separate V0-50 feature source
   to explain.
2. **Parallel worker execution** following the `derived_8.4-eval-2.0` driver/worker format
   (`run_loso.py` spawns n_parallel `run_loso_worker.py` subprocesses; resume via per-fold
   `meta.json` + `data_version`) to utilize the H100 GPU with concurrent XGBoost folds.
3. **sbatch GPU run** with the requested params:
   `--time=01:00:00 --partition=gpu_debug --gres=gpu:h100:1 --cpus-per-task=6 --mem=16000 --nodes 1`.

## Background (verified during planning)

- eval-1.2 = 47 pinned configs (2 baselines + 5 MoE strategies × 9 delta-grid points
  (c0, c1 ∈ {0,5,10}²)) × 7 WA stations; XGBoost (`device: cuda`, seed 42, n_estimators 2500);
  LOSO + full-training baseline + station-similarity analysis. ~1.5 h serial on H100 (329 folds);
  full baseline ~15 min serial.
- Delta additions per (strategy, c0, c1) pinned in eval-1.1's `delta_grid_summary.csv`;
  per-strategy winners in eval-1.1's `metrics_summary.csv` (`Clustering_V0_Full_k2` won at
  c0=0, c1=10).
- eval-2.0 worker format: driver pins configs, spawns `run_loso_worker.py` subprocesses
  (n_parallel), each writes `meta.json` (status + `data_version`); driver aggregates; resume
  skips completed jobs; smoke uses `data_version=-1` so smoke artifacts are never reused.
- Environment: login node has **no GPU** (smoke runs on CPU via `--device cpu`);
  `gpu_debug` TIMELIMIT = 2:00:00 (1:00:00 accepted); xgboost 3.2.0 / sklearn 1.8.0 via
  `uv run` in `notebooks/`; `sbatch` available.

## New strategy design

- **Name**: `Clustering_Backbone54_k2` — KMeans(k=2, n_init=10, random_state=42) on the 54
  `shared_backbone_54` features (the exact feature set of `Global_Single_54`).
- **Router**: `Backbone54Router` in `eval13/routers.py` (identical structure to `V0FullRouter`,
  feature set differs); `get_router()` gains `backbone_54` + `device` args (device also
  threaded into `TrainedGatingRouter`, which previously hardcoded `cuda`).
- **Grid**: full 9-point delta grid (c0, c1 ∈ {0,5,10}²) → 56 configurations total, same
  format as the other 5 MoE strategies.
- **Delta additions**: pinned per grid point from eval-1.1's `Clustering_V0_Full_k2` rows
  (same (c0, c1)) — documented in config.yaml/README: additions stay fixed from eval-1.1
  exactly like the other strategies; only the routing features differ.
- **Winner pin**: `new_clustering_strategy.winner: {c0: 0, c1: 10}` (mirrors the eval-1.1
  V0-Full winner), decided BEFORE running (no post-hoc selection). Marked `is_winner=True`;
  `station_sim.load_difficulty` prefers the new strategy's winner (fallback V0-Full).
- `eval11_test_r2` = NaN for the 9 new configs (no eval-1.1 row). `run_loso.py` backfills the
  temporal reference (`temporal_test_r2`) from `full_config_summary.csv`'s `full_pooled_r2`
  (the full-training/temporal protocol R2) when that file exists — hence the sbatch script
  runs the full baseline FIRST.

## Compute estimate & risks

- LOSO 56×7 = 392 folds × ~35-45 s ≈ 4-4.5 serial GPU-h → **~35-45 min wall at 8 workers**;
  full baseline ≈ 3-5 min parallel; total **~40-50 min < 1 h**. Wall-clock kill → re-submit
  (resume via job meta.json).
- 8 workers × 1 CPU on a 6-CPU allocation → mild oversubscription (eval-2.0 ran the same);
  fallback `--n-parallel 6`. XGBoost per-process GPU memory is small (<1 GB); 8 concurrent
  fits an H100.
- New strategy's grid-point additions reused from V0-Full rows — documented caveat
  (additions fixed from eval-1.1; only routing features differ), consistent with eval-1.2's
  "fixed features" stance.

## Addendum (2026-08-12): 1h-wall finding → eval-1.2 references for the 47 configs

**First GPU run (job 2037010, `--n-parallel 8`, all 56 configs) hit the 1 h wall after
104/448 jobs.** Worker logs showed each XGBoost fold took **128-310 s** (vs ~16 s serial in
eval-1.2): 8 concurrent XGBoost GPU processes serialize on the single H100 (the GPU is the
bottleneck), so the parallel worker format buys resilience/resume but **no aggregate
throughput** for XGBoost. The full workload is ~2 h of GPU time — it cannot fit the user's
`--time=01:00:00`.

**Resolution (implemented):** `--new-strategy-only` scope + eval-1.2 reference merge.
- `run_loso.py` / `run_full_baseline.py` gain `--new-strategy-only`: compute ONLY the 9 new
  `Clustering_Backbone54_k2` configs (63 LOSO folds + 9 full-baseline configs ≈ 72 jobs ≈
  **25-40 min** at `--n-parallel 6`), then merge the 47 eval-1.1 configs' recorded results
  from `derived_8.4-eval-1.2` as references (`is_reference` column; all-or-nothing per
  config). This is the eval-2.0 precedent (XGBoost references merged, no retraining) and
  loses nothing: the 47 configs are deterministic (seed 42, same xgboost 3.2.0 env; eval-1.2
  replicated eval-1.1 to 0.000000). A full run without the flag still computes all 56.
- `n_parallel` default lowered 8 → 6 (1 worker per sbatch CPU; observed CPU thrash at 8).
- `run_slurm.sh` runs both steps with `--new-strategy-only --n-parallel 6`, full baseline
  first (so `run_loso.py` backfills the new configs' `temporal_test_r2`).
- Smoke-verified locally on CPU (data_version -1): reference merge (47 configs, 329 folds,
  pooled LOSO backfill matching eval-1.2's numbers), full-baseline merge + replication check
  (47 configs, max |diff| = 0.000000), resume.

# Plan: `derived_8.4-eval-mlp-1.1` — close the gap to XGBoost

## Part 1 — Analysis of `derived_8.4-eval-mlp-1.0` (what went wrong)

### Results recap (from executed notebook / README / CSVs)
- Best MLP **2-regime** (w256x256_d0.3): pooled test **R² = 0.759** vs XGBoost 2-regime winner **0.815** → **Δ = −0.056**.
- Best MLP **1-regime** (w256x256_d0.3): **0.723** vs XGBoost global **0.779** → **Δ = −0.056**.
- MLP **wins on OOD slices** (+0.076 R² 2-regime: 0.695 vs 0.619) but **loses in-distribution** (0.755 vs 0.817) — the in-distribution gap dominates.

### Where the gap lives (diagnosis)
1. **Per-cluster (2-regime):** c0 (73% of test, n=4817): MLP 0.733 vs XGB 0.802 (Δ0.069); c1: 0.820 vs 0.844 (Δ0.024). The majority-cluster specialist is the weak link.
2. **Yearly:** MLP 2025 R² = **0.689** vs XGB **0.830** (Δ0.14) — MLP degrades badly in 2025 (distribution drift); 2023–2024 the gap is only −0.01..−0.03. Fixing 2025 alone nearly closes the pooled gap.
3. **Holdout selection is unreliable:** ranked by the 10%-temporal-tail holdout, the 1-regime winner (w1024x1024, hold 0.0679) has test R² 0.636, while the test-best config (w256x256_d0.3, hold 0.0706) has 0.723. A 0.003 RMSE holdout difference ↔ 0.09 R² swing on test. The 10% tail (~1.4k rows) is too small/noisy.
4. **Underfitting / short training:** cosine LR over max_epochs=200 with patience=25; several configs stopped while still improving (best_epoch ≈ max epochs, e.g. 2regime bs256: best 122/147). Capacity ceiling at 256×256 (81k params).
5. **Ensembling alone won't fix it** (computed offline on existing preds, CPU-only, zero GPU): top-3 2-regime config ensemble → 0.761 (+0.002), top-4 1-regime → 0.735 (+0.012). Need **better individual models** first.

### Root cause framing
XGBoost (2500 trees, lr 0.005, depth 9, strong regularization) is a massive tuned ensemble trained on the full trainval (14,608 rows). The 1.0 MLP was: (a) a single network, (b) trained on ~90% of trainval with a small noisy holdout, (c) capacity-limited, (d) early-stopped too early. Each of these is addressable.

## Part 2 — Plan for `derived_8.4-eval-mlp-1.1`

**Goal:** match or beat the XGBoost references (2-regime 0.815, global 0.779) with neural tabular models, within ~1 h of H100 wall budget (sweep itself is only ~5–15 min; the rest is dev + report).

### Key protocol changes (vs 1.0)
1. **Official val split for early stopping / config selection (data_version 3).** Train on `train` (2017–2020, 9,803), early-stop on `val` (2021–2022, 4,805 — 3.3× bigger than the 10% tail, exactly mirrors the temporal test construction). Router (V0FullRouter k=2, seed 42) still fit on trainval for comparability with eval-1.1.
2. **Retrain winner on full trainval** (train+val, 14,608) at fixed best-epoch count → final leaderboard rows (matches XGBoost's trainval training; +49% data vs 1.0).
3. **Longer / better training:** max_epochs 400, patience 60, warmup (5%) + cosine LR, optional EMA, huber-delta parameterized.
4. **Ensembling (the NN analog of 2500 trees):** 5-seed average of the winning config + average of top-3 configs' predictions.
5. **Architecture + feature expansion (cheap to run, guarded):**
   - Residual MLPs (ResBlock: Linear→BN→act→Linear→BN→+skip→act).
   - **FT-Transformer** (feature tokenizer + TransformerEncoder + head) — the strongest tabular NN; smoke-tested early, dropped if it misbehaves.
   - Categorical embeddings for `J_lc_code`, `J_soil_texture_usda_b0` in the plain MLP.
   - **96-feature candidate-pool families** (62 informative features beyond the 54 backbone) — tests whether MLPs benefit from richer inputs than the XGBoost-tuned backbone.

- Residual: res_w256x256_d0.2, res_w512x256_d0.2, res_w512x512_d0.2, res_w256x256x256_d0.2
- FT-Transformer: ft_d32_l2, ft_d64_l2, ft_d32_l4, ft_d64_l4
- Misc: _bs1024, _ema, _huber(d0.1), _ln (LayerNorm)

Jobs ≈ 26 × 4 = 104 sweep + ~20 retrain/ensemble (5 seeds × 4 winners) ≈ **~8–15 min GPU** at 8 parallel workers (1.0 did 54 jobs in 2.1 min; FT-Transformer is the slowest per-epoch but still seconds).

### Risks / notes

- Categorical columns (`J_lc_code`, `J_soil_texture_usda_b0`) get learned embeddings in the plain-MLP path; FT-Transformer embeds them via its tokenizer.
